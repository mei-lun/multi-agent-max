# LevelUp 创作空间接入 MAM：只读上游移植与持续同步计划

日期：2026-11-06。执行开始：2026-11-07。当前状态：0.1.43集成至MAM主分支；实际完成范围及外部验收边界见[交付清单](../../acceptance/2026-11-08-creative-delivery.md)。本文保留目标与验收要求，不代表真实模型/GPU/macOS项目已全部验收。

调查基线：LevelUpAgent 1.5.93，提交 `6542241`；MAM 工作区版本 0.1.39，基准提交 `51091d8`。实施时以锁定的完整提交 SHA、来源文件和依赖清单为准。

## 1. 目标、范围与约束

将 LevelUp 创作空间的六个工作台移植为 MAM 可选组件，并建立持续同步机制。用户可以自行安装，通过工作台手动操作、授权角色调用工具，或在 MAM 工作流中执行组件操作；三条路径使用同一套 MAM 组件业务实现。

### 1.1 功能范围

包含图片/视频/语音、音乐、写作、星图、Spine、3D，以及各工作台已有的编辑、工程、历史、任务恢复、资源管理和导出功能。组件划分见第 2 节，逐功能接入和验收见第 6 节。

不包含桌宠、聊天机器人、主题管理、Armor、LevelUp 全局桌面设置或完整 LevelUp Agent Executor。创作所需的文字/视觉推理、会话执行和工具权限接入 MAM 现有能力。

本期不扩展 Linux 全套发行、macOS 本地完整音乐/3D 推理、星图的音乐/Spine/3D 新节点、第三方组件市场、远程 GPU/设备调度、模型训练或多人实时协同编辑。

### 1.2 只读上游与持续同步

LevelUp 独立开发和发布，其源码、配置、依赖锁、文档、CI、用户数据及原工作区的 `.git` 均不得改动。所有抽取、重构、适配、补丁、构建、测试与组件发布都在 MAM 仓库或其专用临时目录中进行。

MAM 保存固定版本的原始源码快照、文件/符号映射和独立适配补丁。后续按上游差异更新、重放补丁、处理冲突、验证并发布组件；生产构建和运行不依赖用户本机的 LevelUp 工作区。源码布局与同步流程见第 7 节。

### 1.3 平台范围

| 平台 | 本期交付要求 |
| --- | --- |
| Windows x64 | 优先验收全部创作功能；本地推理使用已验证的 NVIDIA GPU 和对应引擎资源 |
| macOS | 保留 MAM 基础与原有发布门禁，验收云端媒体、写作、星图及可移植编辑能力；不要求本地完整音乐/3D 推理 |
| Linux | 保留导入代码已有的可移植边界，不作为本期完整创作发行目标 |

组件按具体操作报告平台支持和资源状态，分别标明可编辑、可生成、可导出及缺少的依赖。安装状态正确不等于功能实测通过。

### 1.4 完成标准与估算前提

全部 50 个工作项须有实现、入口、平台条件和验收证据。除初次接入外，必须完成从旧上游提交同步到含真实修复的新提交的演练，确认修复生效、冲突可审阅、旧任务可继续且原 LevelUp 工作区无变化。

工时按熟悉 TypeScript/Electron、Rust 和 Python 的工程师计算，1 人日约 8 小时、1 周为 5 个工作日，包含模块定向测试和联调。假设 API 配额、GPU、macOS 验收机器、必要软件及资源分发条件可取得；外部等待影响日历周期。工期在 P0 原型后校准，汇总见第 10 节。

文中的 API、组件 ID、目录和新增状态均为拟定契约。

## 2. 产品形态：六个入口、八个可选组件

图片、视频、语音可以独立安装，在界面上共用“图片·视频·语音”入口；其余五个工作台各是一个组件。组件中心允许一键勾选整套创作空间，也允许单项安装。

| 组件 ID（拟定） | 用户获得的内容 | 必需依赖 | 可选增强 |
| --- | --- | --- | --- |
| `creative.image` | 图片生成、编辑、扩图、重绘、历史 | 媒体运行时、画板处理库 | 配置支持对应操作的模型 |
| `creative.video` | 五类视频操作、任务和作品管理 | 媒体运行时 | 图片组件；不强制安装，可导入已有图片 |
| `creative.speech` | 语音生成、音色、试听和导出 | 媒体运行时 | 对应语音服务 |
| `creative.music` | 音乐工作台、作品库和剪辑 | 音乐控制进程 | ACE-Step、YuE2、MusicGen 资源分别安装 |
| `creative.writing` | 文稿、设定、参考库、Goal、剧情 | 文档工程库、文字推理接口 | 已配置的文字模型 |
| `creative.spine` | 骨骼编辑、姿态、动作、工程和导出 | Spine 算法及图像/渲染服务 | 图片生成、ComfyUI、RIFE、视觉模型 |
| `creative.model3d` | 模型工程、预览、形状/贴图/绑定 | 3D 启动器、查看器 | runtime、TripoSG、贴图、Blender 资源按阶段安装 |
| `creative.constellation` | 星图项目、12 类节点和蓝图 | 星图执行与工程库 | 图内实际用到的组件 |

依赖边界：画板和基础图像处理是共享库，图片和 Spine 不应强依赖星图；Spine 手动编辑不依赖生图；3D 导入参考图不依赖图片组件；星图打开和编辑不强制安装全部执行组件。作品引用节点保持现有“引用其他星图稳定输出”的语义，其他工作台成果通过统一资产输入接入。

代码包、引擎、模型资源独立版本化。卸载组件可释放代码和无人引用的依赖；作品和项目默认保留。资源清理必须明确目标目录、共享引用及当前占用，不随组件卸载自动删除用户成果。

## 3. 公共架构与接入契约

### 3.1 运行结构

```text
MAM 主界面：组件中心 / 创作入口 / 角色 / 工作流 / 审核
                  |
MAM 主进程：组件宿主 / 能力网关 / Job 管理 / 资产服务
        |                         |
官方组件独立 UI              TS SDK 与后台业务模块
（隔离渲染上下文）                 |
                      媒体 Rust / 音乐 Python / 3D Python
                                  |
                          模型服务与按需安装资源
```

1. 主程序负责 Scheduler Kernel、角色、权限、凭据、Git 权威状态、Attempt、Artifact 和新增的组件宿主。组件不能自行修改 Run 的权威状态。
2. MAM 按第 7 节的来源锁和补丁规则构建组件，业务依赖限定在 MAM 管理的源码、运行包与资源内。
3. 在 MAM 导入的副本中，从 `src-tauri/src/lib.rs` 对应代码抽出媒体和创作服务，改为显式传入数据根、配置、凭据解析器、事件和取消句柄。MAM 只实现自己需要的宿主适配；LevelUp 原 Tauri command 与实现不改动。
4. 每个可选组件交付实际的 UI/业务文件，未安装时不随 MAM 主包携带该组件业务，也不启动进程。图片/视频/语音允许共享轻量媒体运行时；音乐、3D 资源不进入它。
5. 官方组件 UI 建议使用独立、sandbox 开启、contextIsolation 开启、Node 关闭的 Electron WebContentsView，通过本机自定义协议加载已验证组件文件。主进程只能接收组件专用的窄接口消息；不能扩大现有主窗口 IPC 的信任范围。
6. 工作台可见窗口关闭后，业务任务仍由 Job 服务持有。Canvas/WebGL 任务使用受管的离屏渲染上下文，不能依赖用户正打开某个页面；这一方案需在 P0 原型核验后固定。
7. 独立后台进程用于生命周期和故障隔离，并不自动构成操作系统级沙箱。首期按官方可信组件分发，第三方原生代码执行策略后置。
8. 工作台编辑器、交互 controller、表单和预览尽量保留上游逻辑，通过 MAM 侧的 token、受限 slots、HostServices 和可追溯补丁适配。MAM 内使用自己的语义颜色、字号、键盘和组件规范；原 LevelUp 的全局 CSS、主题和 Armor 不进入 MAM。无法直接复用的重写区域必须列为需人工同步的边界，不能宣称以后自动继承上游 UI 修复。

### 3.2 组件 manifest 与安装

每个 manifest 至少记录：组件 ID/版本、SDK 协议版本、兼容 MAM 范围、支持的 OS/架构、UI 与后台入口、依赖版本范围、可选引擎、能力与参数 schema、资源清单、包大小/哈希/来源、权限声明、工程 schema 与迁移版本。

安装流程：解析依赖 → 平台与空间检查 → 暂存下载 → 大小/哈希与签名检查 → 安全解包 → 注册 → 启动自检 → 标记可用。离线包走同样流程，组件签名与包清单纳入发布产物。

升级采用旁路目录；任务固定组件版本与内容哈希，运行中不替换二进制。旧版本只有在无运行任务、无恢复引用且数据兼容性允许时才回收。工程迁移先备份；需要降级时恢复迁移前副本，不能假设旧版本能读新 schema。

### 3.3 三种使用路径

| 路径 | 调用和权威归属 | 完成条件 |
| --- | --- | --- |
| 手动创作 | 工作台 → 组件网关 → 本机 Job；创建本机创作工程，不自动创建 Workflow 或独立 Agent Session | 成果落盘、可再次打开；用户可选择提交给指定任务或导出 |
| 角色工具 | Role 勾选组件 → 在既有 Pi Application API 中新增组件调用入口 → 组件 Job；绑定当前 Attempt | 调用结果和资产清单返回当前 Attempt，由 MAM 验证后交付 |
| 工作流直接调用 | 新增 `component_task` 节点，设计时固定一个 Role、组件操作、输入和输出契约；建立正常 Task/Attempt | 组件完成、成果校验、预算检查通过后，由 Kernel 推进审核或下游 |

拟新增 `component_task` 作为组件任务节点，使用异步 Attempt 执行分支。直接调用剪辑、导出或生成 API 时无需先启动对话模型。角色提供授权与归属，重试、返工、Claim fencing、Artifact 和审核沿用 MAM；现有 Role 的 Executor 配置保持合法。

角色工具通过 `component.invoke/status/cancel` 等统一入口接入；需要更新现有 Application API 的 schema 和官方桥接实现，不能仅在 Prompt 中列出不可调用的工具。图中长任务使用后台执行，不加入当前同步 `advanceReadySystemNodes` 循环。

### 3.4 统一 Job 与事件

建议服务面：`describeCapabilities`、`submit`、`getJob`、`subscribe`、`cancel`、`listArtifacts`、`export`、`dispose`。短查询可以直接返回，生成/安装/拟合操作返回 Job ID。

请求记录：component ID/version/hash、operation、input asset refs、参数、project ID、可选的 Run/Task/Attempt ID 与 claim generation、权限/模型快照、预算、幂等键和 deadline。身份字段由宿主绑定，组件不得自行声明另一个 Attempt。

事件记录：job ID、递增 sequence、phase、progress、log、artifact、usage、approval request、failure 和终态。重连从 sequence 恢复，并处理慢消费者背压；stdout 只承载协议，stderr 承载日志。

区分“请求已接收”“生成已结束”“结果已校验”“已提交 MAM”。取消记录为 requested/confirmed/unknown，不能把停止轮询描述为取消云端生成。进程退出或提交响应丢失时先用上游任务 ID 对账；无可靠查询/幂等能力时进入人工核对，不自动重发付费请求。

本机 Job 数据库保存运行日志和恢复信息；MAM Git 事件保存权威工作流状态。取消后晚到成果可进入本机历史，但不得推进已取消或已被新 generation 取代的 Attempt。

### 3.5 资产与二进制 Artifact

现状：MAM `file-set` 是 `{ path, content: string }`，收集时按 UTF-8 解码；Artifact 契约最大 100 MiB。需要增加独立二进制资产格式，保留原有文本格式及限制。

- 新增 `asset-bundle` 契约：manifest 列出内容哈希、实际字节数、MIME、逻辑文件名、尺寸/时长、来源资产、组件/引擎/模型版本、参数和所属 Attempt。资源路径必须可移植，不能以源机器绝对路径作为唯一定位。
- 草稿和生成中成果放本机内容寻址存储；提交时冻结资产清单和所有资产内容，已审核成果不可原地修改。人工编辑从冻结版本派生新版本。
- 正式资产清单进入 Git；小二进制可进 Git，大二进制拟采用 Git LFS 指针及对象。LFS 本地对象可支持无 remote 的本机流程；跨 clone 交付必须核验目标能取得对象。无 LFS 环境时可显式导出/导入带哈希交付包，缺对象阻止下游。
- LFS 和大对象存储是新增交付机制，P0 须明确 Git 内容与外部对象的关系，经设计审阅后更新 MAM 产品权威定义；只记录本机 CAS 路径不能满足跨 clone 交付。
- 项目源码变更仍遵守原有 worktree、commit 和 merge ancestry 规则；普通媒体 Artifact 不应为了传递文件强制走源码合并。
- 预览服务支持 PNG/JPEG、音视频、GLB 和工程清单；通过受控本机资产协议传输，支持音视频 Range。IPC 不携带大块 Base64，代理图不能代替原文件。
- 工程引用采用稳定资产 ID；删除检查引用关系。缩略图、缓存、模型权重、作品分别管理，不能混用清理入口。

### 3.6 模型、权限与平台

复用 MAM 的 Provider/Model 与 secretRef。新增创作模型配置/能力 schema，区分文字、视觉、图片输出、语音、视频和本地引擎，保留服务特有参数与已确认能力。当前 text/image/audio 枚举不能直接表达所有创作操作。

写作与 Spine 使用无工具文字/视觉推理服务；优先抽取 MAM 现有 Model Gateway，缺少的流式/视觉/协议能力纳入 F4 补齐。图片/视频/语音复用 LevelUp 媒体协议适配。模型在 Attempt 开始时固定，失败不自动切换 Provider、模型或本地引擎。

共享硬件管理先实现按本机 GPU 的排他队列及内存/磁盘前置检查，覆盖音乐、3D 和本工具发起的 RIFE。它无法控制其他软件或独立 ComfyUI 的全部显存使用；外部负载需要检查并报告，不能声称获得全机独占。

平台能力细分到操作，例如 3D “查看/导出”与“CUDA 生成”分别报告。卸载全部推理资源后，已保存作品仍可查看和导出。

## 6. 每个工作台的详细迁移

下表中的操作名均为建议 API。每一行都要求：SDK 可调用、需要的交互有工作台入口、角色/工作流可获得结构化结果、操作可取消或明确说明无法取消。

### 6.1 图片、视频、语音（12–18 人日）

```text
  vendor/levelup/                 # 固定提交中的原始源码与必要来源材料
  migration/levelup/
    upstream.lock.json           # 上游提交、文件哈希、资源与依赖版本
    source-map.json              # 上游文件/符号 -> 组件/下游文件/测试
    patches/                     # 按能力拆分、有顺序与理由的下游补丁
    transforms/                  # 确有需要时使用的可重复抽取/导入改写
  packages/creative-*/            # MAM SDK、公开接口、适配和工作台入口
  crates/creative-media/         # MAM 所需的 Rust 构建入口与适配
  config/scripts/levelup-sync/   # MAM 侧的差异、合并、校验和报告工具
  .cache/levelup-port/            # 可重建的中间源码/构建产物，不作为手改源
```

优先保留导入源码的文件布局和名称，在 wrapper/adapter 中解决差异；大型 React/Tauri 文件需要抽取时，记录原文件、符号范围、相关私有依赖和转换版本。MAM 内的公共图像、资产和 Job 库供多个组件复用。

生产组件由“锁定的上游快照 + 版本化补丁/转换 + MAM 适配代码”构建。原始快照不手工编辑，生成目录不接受人工修复；修复回到补丁、转换或适配代码中，确保干净目录可以重建相同来源关系。编译结果是否字节完全一致受工具链影响，但源文件重放结果和输入哈希必须确定。

MAM 已有 `migration/source-selection.json` 和 `generate-source-manifest.mjs` 的来源文件/目标哈希记录模式，可以复用其思想；增加单独的 LevelUp 清单，不覆盖既有 MAM 迁移来源记录。现有脚本只生成来源记录，尚不具备本计划的三方合并和补丁重放能力。

不能把 LevelUp 的 `src/lib/bridge.ts` 原封不动作为 SDK：其中含 Tauri、预览 mock、文件选择和全局状态。所有依赖改写在 MAM 副本中通过显式 HostServices 完成；浏览器预览 mock 不进入生产 SDK。保留必要的上游测试、资源 manifest、LICENSE/NOTICE 和依赖版本作为输入，不能只复制一个入口文件。

工程数据采用用户显式导出/导入，不共享两应用正在写入的 SQLite/IndexedDB。写作/星图沿用现有导出格式；Spine 使用自包含工程。现有导出不能覆盖的媒体、音乐、3D 数据，由 MAM 导入器读取用户提供的只读副本并创建新工程；不得要求 LevelUp 新增导出功能，也不通过启动原应用做自动迁移。保留 source ID/版本/哈希，源数据不改写，凭据重新映射到 MAM。

### 7.3 持续跟随 LevelUp：原始快照、下游补丁与差异同步

#### 7.3.1 来源与改动归属

```text
LevelUp 独立开发、修复、发布（只读上游）
                    |
       MAM 获取明确提交的源码与资源清单
                    |
       原始快照 + MAM 补丁/转换 + 适配层
                    |
       候选组件构建、来源对比与 MAM 回归
                    |
       MAM 组件发布目录 -> 用户选择更新
```

| 层次 | MAM 如何管理 | 后续更新方式 |
| --- | --- | --- |
| 上游原始源码 | 固定完整提交 SHA，保留选择的原文件字节及哈希 | 从新提交替换候选快照，不手改快照 |
| 上游算法、校验、导出与 worker 的移植结果 | 尽量原样复用；必要改动放最小补丁 | 依据旧/新上游差异重放补丁，检查行为 |
| React 工作台及业务 controller | 保留上游逻辑，宿主接线和样式改动单列 | UI 变更同样做差异分析；改写区需人工确认 |
| MAM HostServices、SDK、权限、Job、资产 | 在 MAM 中维护独立适配层 | 上游接口/状态变化时更新对应端口 |
| MAM 特有增强或临时 bug 修复 | 使用单独且有理由的补丁，关联能力和回归样例 | 上游已包含修复时撤销对应补丁，避免重复应用 |
| LevelUp 的桌宠、机器人、主题及桌面设置 | 不进入创作组件包；必要依赖检查时仅分析其引用关系 | 不主动同步其产品功能；避免遗漏跨文件公共依赖 |

下游差异必须可追溯和可验证；发生冲突或行为变化时，先处理并通过测试，再推广新组件。

#### 7.3.2 快照与补丁规则

每个 `upstream.lock.json` 至少记录来源 URL、完整提交 SHA、可选 release/tag、原始文件路径/哈希、依赖锁与资源版本、选择规则版本。发布集额外记录补丁/转换/适配提交及哈希、包版本、OS/架构、MAM Host API 和工程 schema 兼容范围。

`source-map.json` 对每项能力记录上游文件/符号、下游组件与文件、导入方式（原样/补丁/抽取/重写）、依赖、人工适配原因和对应测试。重写区域明确标记“人工同步”，其上游变化必须出现在报告中，不能因为不直接导入而漏掉。

MAM 适配补丁按目的分开：路径/模块导入、Tauri 替换、存储、权限、UI 外观、行为修复。禁止在一次大规模格式化补丁里混合业务变更。导入声明或符号抽取优先使用可解析的结构化转换；文本补丁要求精确上下文和预期匹配数。缺失/重复锚点、依赖漏选或模糊匹配均停止同步，不静默跳过。

如需三方合并，使用“旧上游内容 + 新上游内容 + 旧上游上的 MAM 修改”在临时候选树计算；冲突解决后必须重新表达为针对新快照的补丁/转换，并从干净快照重放验证。不能只保存人工改过的合并产物，否则下一次无法重复。

更新相关依赖时读取上游 lockfile 和实际 import/use 引用，同时检查新增辅助文件、资源及测试；不能只按既有目录列表筛出修改文件。Rust 聚合文件抽取需要显式维护依赖闭包，Python worker 与运行包的依赖也必须纳入。

#### 7.3.3 一次更新的完整流程

1. 由维护者指定目标上游提交或已核验的 release。MAM 同步工具在自己的镜像/暂存目录读取来源，不在用户原 LevelUp 工作区执行 fetch、checkout、install、build 或写入操作；本机取源码时用已提交 blob，不能悄悄携带未提交内容。
2. 比较当前锁定基线与目标提交，报告改动的功能、文件/符号、依赖、协议、资源和工程格式。检测重命名/删除，但视为需要确认的映射，不能只靠路径相同判断无变化。
3. 扩展所需依赖闭包，生成“可直接更新 / 补丁冲突 / 需要适配 / 范围外”清单。原基线和已发布包不变。
4. 在 MAM 候选树应用补丁和转换，进行三方合并。能干净应用的差异进入自动检查；冲突、行为差异、权限扩大和新增资源进入人工处理。
5. 重建受影响组件及传递依赖，运行可复用的上游测试、移植适配测试、SDK/工作台/角色工具/component_task 测试。对比源样例和新输出，确认修复在 MAM 实际生效。
6. 对受影响的 GPU、付费服务、图像质量和工程迁移完成必要实测。测试源代码需要执行时，将原始锁定源码复制到 MAM 临时目录，用隔离数据执行；不用原工作区和用户数据，读源码本身不等于功能验证。
7. 生成可审阅更新报告、MAM 组件候选包及新的来源锁文件。明确继承了哪些修复、哪些新增功能暂未适配；只有通过验收的能力才能标为已同步。维护者审核后发布兼容目录。
8. 用户在 MAM 组件中心更新已安装组件；运行中任务保留原版本，新任务使用更新后版本。失败保留已发布基线；数据迁移须有备份，能够恢复旧组件及相应数据。
9. 上游如已原生修复某个 MAM 本地补丁，证明等价后移除补丁并运行其回归测试。上游变化不要求回写或提交 PR 到 LevelUp。

同步入口由维护者指定目标提交触发，检查、候选构建和发布均在 MAM 侧运行。上游版本发现可作为后续自动化扩展，不影响本期手动触发的完整同步流程。

#### 7.3.4 不同更新的处理边界

| 上游变化 | MAM 处理 | 能否预期快速同步 |
| --- | --- | --- |
| 未改写区域的算法/解析/导出 bug 修复 | 更新来源文件、重放现有补丁、验证回归 | 最有机会自动合并；干净合并仍需测试 |
| 已改写区域的同类修复 | 根据来源映射移植修复，重算本地补丁 | 需要人工理解差异，不能只复制新文件 |
| 界面操作、交互和预览修复 | 合并源组件/controller，重放 MAM 接线与外观补丁 | 取决于 UI 改写程度，需视觉和交互验证 |
| 新参数、新模型、新操作 | 更新实现和能力声明；检查模型/权限及 MAM 表单 | 已有扩展接口可承接时较快，未适配项明确列出 |
| 新文件类型、Tauri 调用、审批方式 | 扩展 MAM HostServices、资产/权限或任务适配 | 可能需要发布 MAM 主程序 |
| 工程 schema、资源、Python/CUDA/原生库变化 | 迁移、资源重建与真实平台验证 | 另行评估，不能保证普通补丁时长 |
| 上游架构大改或文件拆分 | 更新来源映射和提取规则、重做必要适配 | 会增加同步成本，重新估算 |

MAM 内部组件仍可共用自己的图像库、Job 和资产服务；同一个上游修复可能影响这些共用层，须通过依赖图重建所有消费者。UI 包和静态链接的原生二进制必须重新构建，不能只更新来源锁文件就宣称用户已获得修复。

#### 7.3.5 组件发布与版本关系

- LevelUp 版本、来源提交、MAM 组件版本、资源版本分别记录；上游版本升级不等于所有功能都已适配。
- MAM 生成不可变 `creative-release-manifest.json`，包含来源锁、补丁/转换/适配哈希、完整依赖、支持平台和测试证据。组件目录展示上游已发现版本、当前已同步版本、本机安装版本及待适配事项。
- 兼容的 MAM 组件更新可以独立于 MAM 主程序发布；新增 Host API、权限、Artifact 格式或无法兼容的数据结构时，升级主程序后再开放对应组件。
- 发布矩阵验证当前稳定 MAM 和前一个仍受支持的稳定版本；LevelUp 仅是来源及行为参考，不是需要配合发布或强制运行候选包的消费端。
- 组件安装锁定精确依赖图，旧任务保留旧组件与资源；不兼容版本并存，不原地替换正在使用的共享运行时。
- 原始快照和补丁保留完整来源/许可材料；数据回退使用备份或兼容读取器，不假设 schema 自动可逆。
- 不自动跟随 main/latest，不静默扩大角色授权，不因上游引入 fallback 而改变 MAM 固定模型策略。

#### 7.3.6 各工作台的同步重点

| 工作台 | 来源跟踪重点 | 容易发生冲突的 MAM 适配 |
| --- | --- | --- |
| 图片/视频/语音 | 模型能力、媒体协议、蒙版、轮询/下载、历史与编辑交互 | Tauri 桥、素材路径、凭据、Job/Attempt 与预算 |
| 音乐 | Python 控制器/worker、参考处理、剪辑、队列、资源清单、作品 UI | 目录、GPU 队列、取消/退出、审核试听 |
| 写作 | 上下文、建议应用、Goal 子步骤、剧情 DSL、编辑器与导出 | 模型服务、存储、父任务与成果冻结 |
| 星图 | 12 类节点、图校验、拓扑执行、蓝图、画板、源码中的新节点 | 会话/工具执行、状态和资产传递 |
| Spine | 校验、骨骼/网格/动作、拟合、编辑器、Comfy/RIFE 和导出 | DOM/离屏渲染、IPC、图片服务、权限与资源路径 |
| 3D | launcher/worker、预处理、形状/贴图/蒙皮、查看器与资源 | GPU 生命周期、工程目录、资产协议和 Artifact |

LevelUp 后续新增功能须进入同步报告并按用户既定范围判断。既有创作功能的修复优先同步；新引擎、新平台或新的大工作台不能仅凭出现在上游就算入原固定工期。

#### 7.3.7 持续同步工作包（12–20 人日）

本工作包负责来源治理、差异合并、补丁重放和同步演练；各领域的首次代码抽取、接口与宿主接线已计入对应迁移工作包，不重复计费。

| ID | 工作 | 验收标准 | 人日 |
| --- | --- | --- | --- |
| G1 | 只读来源获取、快照/依赖锁、文件/符号映射、补丁布局与目录边界检查 | 来源可验证，原工作区无写入；源片段、依赖、资源与许可能追踪；重写区显式标记 | 3–5 |
| G2 | 新旧差异分析、三方合并、精确补丁/转换重放与依赖闭包检查 | 普通修改可重放；改名/删除/新增依赖/冲突不漏报；从干净快照重建，失败保留旧基线 | 3–5 |
| G3 | MAM 候选构建、来源行为对比、组件/宿主兼容测试与同步状态报告 | 构建不读取原 LevelUp 目录；原测试只在下游隔离副本执行；遗漏或失败项不能标记为已同步 | 3–5 |
| G4 | 实际上游修复同步、UI 差异、冲突、新依赖、版本保留和回退演练 | 从两个实际已提交版本继承至少一项真实修复；冲突/新增依赖可用 MAM 内的测试 fixture 演练；源工作区不变 | 3–5 |

G1 从 P0/P1 开始；G2 随首个可安装组件建立；G3 在第二个组件前跑通；G4 作为 P8 出口。未来所有模块按相同规则加入，不能等迁完后再补来源关系。

#### 7.3.8 后续维护时间与承诺边界

以下是流水线就绪后的主动维护时间目标，尚需真实上游更新演练校准；构建、GPU 任务、外部服务和下载等待另外影响日历时间，不是发布 SLA。

| 后续更新 | 初步主动维护目标 | 条件 |
| --- | --- | --- |
| 小型业务修复、没有补丁冲突 | 0.5–2 人日 | 依赖未改变，现有回归与 MAM 验证通过 |
| 局部 UI 修复、常规新参数或小范围适配冲突 | 1–4 人日 | 需人工审阅接口/交互和源差异 |
| 大型重构、新宿主调用、工程 schema 或 GPU 资源变更 | 按差异估算，可能数日至数周 | 不承诺无冲突或自动移植 |
| 一个上游版本同时更新多个工作台 | 根据影响分析重新排期 | 上述单项估算不能直接作为整版更新时间 |

持续同步的验收目标：来源基线明确、相关差异可发现、适配补丁可重放、冲突集中展示、继承的修复经测试验证，最终能够独立发布组件。

| Q3 故障与多实例 | 进程崩溃、断网、晚到结果、取消、重启、重复提交、Claim 接管、两 clone | 不重复付费提交；无遗留 GPU worker；旧 generation 不能交付；缺 LFS 对象阻止下游 | 2–3 |

| Q5 发布与维护文档 | SDK 示例、组件制包、版本矩阵、安装/迁移/恢复说明、签名与资源清单 | 每项功能关联 evidence；可下载的发布包与测试包一致；更新版本档案与 traceability | 2–3 |

必须具备的业务样例：

1. 图片：批量生成→选图→蒙版编辑/扩图→历史复用→导出。
2. 视频/语音：参考图生成视频＋文字转语音；期间关闭页面、重启并恢复；检查实际文件与播放。
3. 写作：设定与参考→文稿建议→接受→Goal→剧情分支→试玩→导出→恢复快照。
4. Spine：整图→拆件→生成或导入图层→绑定→动作→姿态研究→导出；ComfyUI 与 RIFE 各有独立真实样例。
5. 音乐：三个引擎分别生成；YuE2 参考改编/去人声；裁剪淡入淡出→导出；资源卸载后试听。
6. 3D：非对称参考图→形状→贴图→关节/权重→三个动作→GLB/FBX/完整工程。
7. 星图：覆盖全部 12 类节点；并行支路失败隔离、局部运行、跨图引用、蓝图导入缺组件、取消后晚到结果。
8. MAM：角色调用创作工具→Artifact→人工审核→同一固定角色返工→新 Attempt；直接 component_task 路径同样验证。
9. 持续同步：选择包含真实功能修复的两个 LevelUp 已提交版本，在 MAM 候选树完成差异同步并验证该修复生效；另覆盖 UI 改动、补丁冲突、新依赖识别、不兼容更新拦截、旧任务版本保留和失败回退。原 LevelUp 工作区始终不变；该演练计入 G4。

必跑检查：在 MAM 使用 `corepack pnpm verify`、阶段性定向 Vitest，发行前补充 `corepack pnpm verify:final` 的组件与来源可追溯要求。移植的 Rust crate、Python worker 和上游回归测试在 MAM 目录或隔离临时副本中执行；不得在原 LevelUp 工作区安装依赖、构建、生成测试产物或改配置。正式收尾执行 MAM 生产打包与真实组件生命周期验证。GPU/云端调用、视觉验收和单元测试分别报告，模拟成功不能代替实机证据。

## 11. 风险、约束与阶段调整

| 风险 | 具体处理 | 何时重新估算 |
| --- | --- | --- |
| React 内混有业务调度、DOM 图像处理 | 先抽 controller/纯算法/HostServices，离屏原型验证；保持黄金输出 | P0 无法离屏复现，需新 native/WASM 后端 |
| MAM 原有语义和新节点冲突 | component_task 固定 Role；Kernel 独占状态写入；更新权威与版本解码，旧 Run 不重算哈希 | 出现不可兼容旧事件或新的调度概念 |
| 正式成果只有本机路径 | Git manifest + 对象哈希 + LFS/显式交付包；缺对象阻止运行，保留跨 clone 证据 | 需加入新的远端存储供应商或同步服务 |
| 多任务争用 GPU | 初期串行 GPU 作业、队列和取消；检查外部负载；不同引擎隔离环境 | 要求多 GPU 自动分配或并行推理 |
| 本地模型不可迁移/资源损坏 | 固定资源版本与来源、干净机器安装、实际推理自检 | 需重新编译 CUDA 扩展或更换模型 |
| 云端提交状态不明 | 先持久幂等键/请求标识、后提交、记录上游回执；支持查询时对账，否则人工核对 | 新供应商没有可恢复语义 |
| 当前已有能力缺实机证据 | ComfyUI/Spine 编辑器等单独列验收项；不能以已有文档或 mock 勾选完成 | 实际模型质量/兼容性不达标 |
| 数据迁移影响用户已有工程 | 显式导入为新项目、迁移前备份、保留原 ID 来源和素材哈希；恢复旧副本 | 无法从现有导出格式恢复完整资产 |
| 下游补丁增多或上游架构变化 | 保留原始快照、最小目的补丁和来源映射；三方合并后从新基线重放；重写区域明确人工同步 | 上游大规模拆分、私有依赖变化或 MAM UI 需大面积重做 |
| 上游更新与 MAM 兼容滞后 | 来源版本与已验证版本分别记录；候选包测试、保留最后兼容版、按传递依赖重建；不自动跟随 main/latest，也不要求 LevelUp 改发布方式 | 新权限、原生依赖、工程 schema 或宿主协议不兼容 |
| 同步工具误写原项目 | 独立 MAM 来源缓存、从已提交 blob 取快照、所有写路径限定到 MAM/专用临时目录；原工作区前后核对 | 工具需要原项目写权限时必须改造工具，而不是默认扩大权限 |
| 源码和资源分发约束 | 保留源项目与引擎的许可、来源和版本记录；发布前由维护者核实分发安排 | 需要替换不能按预期分发的依赖 |

缺少验收证据的工作项保持未通过，不从覆盖清单中删除。预览版须标明可用范围；完整交付要求 B/F/M/W/S/A/D/C/Q/G 共 50 项全部通过。
