# 设计助手不可用故障复盘（2026-09-20）

## 文档目的

本文记录 2026-09-17 至 2026-09-20 期间 Design Assistant 无法通过 OpenAI 中转正常生成设计的故障链、诊断依据、根因、修复方法和防回归要求。

本文对应最终修复版本 `0.1.26`。它不是新的产品设计；产品语义仍以 [`final-reuse-integration-plan.md`](../final-reuse-integration-plan.md) 和 [`MAM_REQUIREMENTS_DELTA_2026-07-27.md`](./MAM_REQUIREMENTS_DELTA_2026-07-27.md) 为准。

## 结论

故障不是 API Key 无效，也不是单一 Provider 超时，而是以下问题连续叠加：

1. OpenAI 中转地址没有统一归一化，模型发现和消息请求可能落到错误的操作路径。
2. Responses 请求没有沿用可用客户端的流式与推理强度契约。
3. 2026-09-17 的 `3542eba` 将原本用于等待 Provider 的 90 秒计时器变成了完整响应的硬截止时间，导致已经收到 `200` 和 SSE 首帧的请求在正文完成前被丢弃。
4. 长响应恢复后，模型返回中存在可由本地 Schema 确定处理的额外字段和缺省 Review 边界值；严格解析在进入 MAM 静态检查前拒绝了响应。
5. 解析或编译失败会触发最多三次自动模型修复，造成后台存在多条成功且计费的生成记录，但 UI 始终没有助手回复或候选工作流。

最终修复遵循两个边界：Provider 请求只负责取得一次模型响应；Schema、引用和 Workflow 编译规则由 MAM 本地确定性处理，不通过隐藏的重复模型调用修复。

## 用户可见症状

- `openai-responses` 模式最初无法正确获取模型列表。
- OpenAI Compatible 可以获取模型，但 Design Assistant 消息不能稳定完成。
- Provider 后台显示 `/v1/responses` 已生成、已计算 Token 和费用，MAM UI 仍显示超时、`fetch failed` 或 Schema 错误。
- Responses 请求最初显示为同步且没有推理强度；修正后显示为流式和 `Medium`，但完整正文超过 90 秒时仍被客户端丢弃。
- 超时修复后出现以下本地解析错误：

```text
Unrecognized keys: "minimumDecisions", "maxRevisionAttempts"
Invalid input: expected number, received undefined
```

- 一次用户操作在 Provider 后台产生三条连续生成记录，这是自动模型修复循环，不是用户连续发送了三次消息。

## 影响范围

- 受影响入口：`mam:send-design-message`、`mam:retry-design-generation`。
- 受影响协议：重点为 `openai-responses`；OpenAI Compatible 也会受到固定总超时和自动修复循环影响。
- 不受影响：Pi RPC 正式 Task 执行、Git 权威状态、已创建 Workflow、Role Profile 和历史 Run。
- 数据影响：失败请求只修改本地 Design Draft 与 recovery 信息，不创建 Run、Task、Attempt 或 Review。
- 费用影响：Provider 已完成但 MAM 丢弃的请求仍可能产生 Token 和费用；旧自动修复循环最多会把一次用户操作放大为三次模型请求。

## 根因分析

### 1. Provider URL 被当作操作地址和根地址混用

模型发现、Responses 和 Chat Completions 需要基于同一个 Provider 根地址分别追加操作路径。用户输入如果已经以 `/responses`、`/chat/completions` 或 `/models` 结尾，旧实现可能继续追加路径，导致模型发现或消息请求访问错误地址。

修复：新增共享 OpenAI 地址归一化，在保存 Profile、模型发现、Design Gateway 和 Pi RPC 配置中复用；协议选择只决定最终操作路径，不自动切换协议。

### 2. Responses 请求契约与可用客户端不一致

旧 Design 请求使用非流式 Responses，且没有传递推理强度。相同中转在 LevelUpAgent 中采用流式请求，并通过 `reasoning.effort` 传递推理档位。

修复：Responses 请求发送 `stream: true` 和 `reasoning: { effort: ... }`；历史 Profile 没有配置时默认 `medium`；本地解析 Responses SSE 的 `response.output_text.delta` 和终态响应。

### 3. 响应头超时被错误地当作完整生成总时限

`3542eba` 的目标是防止用户取消或重置草稿后，迟到响应覆盖新 Draft。实现将用户取消、Draft 失效和 Provider 超时共用同一个 AbortController，并在正文读取完成后再次检查其状态。

这使 90 秒计时器从“等待 Provider 响应”变成了“完整生成必须在 90 秒内结束”。只要长响应超过 90 秒，即使已经收到 HTTP 200 和持续的 SSE，结果也会被确定性拒绝。

修复：每次请求单独启动响应头计时器；`fetch` 返回响应头后立即清除。用户取消、重置草稿、Draft ID 失效和迟到响应检查继续保留。

### 4. 严格响应 Schema 早于 MAM 静态检查拒绝候选方案

模型可能在不适用的节点上附带 `minimumDecisions`、`maxRevisionAttempts`、`recommendedRoleKeys` 或 `allowedRoleKeys`，也可能遗漏 Review 节点的标准边界值。这些字段偏差可以由 MAM Schema 和标准模板确定性处理，不需要模型重新推理。

修复：

- Review 节点缺少边界值时使用标准模板默认值。
- 首次严格解析后，只按 Zod `unrecognized_keys` 的精确路径删除正式 Schema 明确认定为未知的字段。
- 重新严格解析一次；缺少基本结构、字段类型错误等其他问题仍正常失败。
- 后续引用、图结构、交接、循环和 Workflow 编译继续由 MAM 静态校验。

### 5. 本地错误被放大为隐藏的重复模型调用

旧 `MamDesignProposalGenerator` 最多执行三次完整模型请求。每次修复请求还会携带旧输出和错误，导致输入体积、延迟和费用继续增加。UI 只等待最终结果，因此前两次成功响应对用户完全不可见。

修复：每条用户消息最多调用模型一次。候选方案能够物化但存在静态错误时，MAM 保存助手回复、候选草稿和 recovery 问题，并阻止确认；只有用户下一次显式发送消息或点击重试时才允许新的模型调用。

## 防回归要求

1. Provider 超时测试必须区分 `waiting_response_headers` 和 `reading_response_body`。
2. 收到响应头后，正文超过原响应头时限仍必须成功完成。
3. 用户取消、重置 Draft 和迟到响应不得覆盖当前 Draft。
4. Responses 请求测试必须断言 `stream: true` 和目标 `reasoning.effort`。
5. SSE 测试必须覆盖正常换行结束和无末尾换行的最后事件。
6. 响应归一化测试必须覆盖 Review 缺省值、错误节点上的多余字段和任意 Schema 未知字段。
7. 一次 `send-design-message` 或 `retry-design-generation` 最多产生一次 Provider 模型请求。
8. 候选 Workflow 有静态错误时必须保留助手回复和草稿，并阻止确认，而不是隐藏地调用模型修复。
9. 真实联通验证必须同时核对 Provider 后台记录数、runtime 请求阶段和最终 Draft 状态。

## 排障检查清单

遇到 Design Assistant 再次出现“后台有记录但 UI 失败”时，按以下顺序检查：

1. 从 `runtime.jsonl` 找到相同 IPC request ID 对应的 `request_started`、`response_headers`、`request_completed` 或 `request_failed`。
2. 核对 endpoint 是否与协议一致：Responses 使用 `/v1/responses`，Compatible 使用 `/v1/chat/completions`。
3. 核对 `response_headers` 是否已返回 HTTP 200；若已返回，不要把问题归类为 API Key 或模型发现失败。
4. 比较 Provider 后台总耗时与客户端失败时间，确认是否存在客户端提前中断。
5. 统计一次用户操作产生的 `request_started` 数量；大于 1 时检查是否重新引入自动模型修复。
6. 若 Provider 请求完成但 IPC 失败，优先检查 response normalizer、Schema 和本地 Workflow 编译错误。
7. 不记录或输出 API Key、Authorization、完整 prompt 或完整响应正文；使用 Profile ID、request ID、阶段、状态码、字节数和耗时关联诊断。

## 已知边界

- 收到响应头后的流式正文没有固定总时限，用户可通过现有停止操作取消。
- 无法解析为 Design 响应基本结构的输出仍会失败，但不会自动产生额外模型请求。
- MAM 只移除正式 Schema 明确认定为未知的字段，不自动修正错误字段类型或猜测缺失的业务内容。
- 中转内部排队、模型推理速度和 Provider 计费不由 MAM 控制；MAM 只保证不会因本地错误隐藏地放大调用次数。
