# LevelUp 创作空间接入 MAM：完成度审计与后续计划

审计日期：2026-11-07。代码基线：`codex/creative-components`，`5b020fb`，MAM `0.1.42`。

## 结论

当前是**八个工作台已有代码接入和离线包的开发验收版**，不是完整功能对等版，也不是仅剩配置 API 和下载模型即可完成的版本。仍有实现缺口、工作流交付缺口和独立升级边界问题。

- 八个组件均有本地包；注册、安装、启停、隔离窗口、后台 Job、资产与来源同步基础已经存在。
- 本轮重新运行 55 个测试文件、143 项定向测试全部通过；这证明覆盖到的路径，不证明原始创作空间的每一个操作都能用。
- 尚无一个组件具备“原始全部子功能 + 正式 MAM 交付 + 目标平台真实环境”的完整签收证据。此处的未签收不表示所有操作都不可用。
- “角色调用”“组件任务”“手动工作台”三条路径的能力和权限尚未完全一致。原进度中部分“已实现”应降级为“部分实现”。
- 后端不少逻辑仍随 MAM 主程序发布，因此“以后 LevelUp 修复后快速更新组件”目前只覆盖部分源码与界面，尚未覆盖全部后端。

不采用一个总百分比：原计划 50 个工作项的规模不同，源码存在、fixture 通过和真实业务可用也不能相加。本报告以各层的可交付边界衡量完成度。

## 影响完整交付的发现

P1 表示完整迁移签收前必须处理；P2 表示明确的功能或恢复差异，需要修复或记录可接受的边界。不是所有未运行的测试都算代码缺陷。

### P1-1：组件任务与角色工具的权限不一致

`attempt-component-executor.ts:38` 只检查组件级授权，之后直接提交 Job。相比 `component-tool-gateway.ts:74`、`:106`，此路径没有检查 `componentBindings.allowedOperations`，也没有执行 `requireApprovalFor` 的逐请求批准。配置为只准部分操作的 Role，仍可能通过 authored component_task 执行被禁止的操作。

下一步：共用授权/批准策略；保留请求哈希、冻结模型和 Claim 检查；用真实执行端口验证禁止、拒绝、批准三种分支，而不只测试网关 mock。

### P1-2：组件升级尚不能覆盖全部后端修复

`desktop-creative-factory.ts:2` 至 `:7` 静态导入媒体、文字、Spine、音乐与 3D 服务；组件 manifest 的 `runtimeEntrypoint` 目前只有声明和文件校验，没有生产动态加载路径。Python worker、原 UI 随包升级，不代表 TypeScript 宿主适配器也随包升级。组件版本固定也不能自动固定宿主内嵌逻辑。

下一步：明确“稳定宿主桥 + 随组件版本发布的业务 runtime”的边界，优先隔离进程/RPC，不直接把任意包加载进主进程。把操作目录、参数 schema、业务实现、来源映射和测试随组件版本发布；MAM 只保留授权、凭据、Job、资产、窗口和进程监督。宿主 API 变化才要求升级 MAM。

同时补齐业务级 API：写作 Goal/导出、Spine 工程处理/导出、星图执行等目前主要存在于 UI 内；只有 text.generate/image.generate 不等于这些创作能力已经成为 SDK。

### P1-3：角色生成素材尚不能正式交付给后续角色

`attempt-component-tools.ts:249` 返回 Job 状态、文本和资产引用，Pi 获得元数据，没有把二进制结果导入正式 Artifact 并物化到合同输出路径的工具。`component_task` 的 executor 有此转换，但不等于 Role 工具和手动工作台也有。

下一步：增加受 Attempt/节点授权的成果提交或物化入口，支持手动草稿选入任务。验收“手工/角色生成 → 正式 asset-bundle → 审核 → 下游角色引用”，拒绝越权资产并保留 provenance。

### P1-4：跨克隆交付只有库函数，产品入口缺失

`local-artifact-store.ts:54`、`:57` 有导出/导入方法，生产路径没有调用者。Git 中有清单，并不能让另一台机器获得本机 CAS 的文件。缺对象检测已实现，但不能替代文件交付。

下一步：先接显式交付包导出/导入 UI、IPC 和校验；新克隆、空 CAS 环境走一次真实审核与消费。Git LFS 自动传输可后续做，不必挡住已验证的显式交付。

### P1-5：星图会话节点没有真实会话语义

`packages/creative-constellation/entry.tsx:7` 传入 `threads=[]`，每次只发一次文本请求并构造 `invocation:` ID；已有 threadId 不会加载前文。列会话直接报不支持，打开会话是设置提示框。因此“12 类节点结构已移植”不能表述为“12 类节点全部可用”。

下一步：映射 MAM 现有 Task/Attempt 和可追溯对话记录，实现创建、继续、列出和打开，遵守 MAM 不新增独立 Session 的产品约束。若某种原会话行为不能映射，明确禁用该操作并记录差异，不能用无状态补全冒充继续会话。

### P2：其余确认差异和需要复测的边界

| 项目 | 证据/影响 | 处理要求 |
| --- | --- | --- |
| 同一 Attempt 组件版本可能变化 | `attempt-component-tools.ts:183` 每次 acquire 当前启用版；模型绑定冻结不等于组件版本冻结 | 首次或准备阶段固定版本和包哈希，批准记录一致；升级后旧任务仍用原版本 |
| 手动工作台项目上下文 | `desktop-creative-services.ts:88` 固定 `creative.local` | 组件内部工程可保存，但未按当前 MAM 项目隔离；补项目选择、归属和授权迁移，避免宣称已完成 MAM 项目隔离 |
| 星图文件内容缺失 | `bridge.ts:29`、`text-bridge.ts:7` 只传文件名/MIME/大小 | 对支持格式做有大小限制的解析；其余清楚提示不支持，不能假装模型读过文件 |

| 成本计量未闭合 | component executor 返回 usage unknown，创作服务未形成完整用量回传 | 不宣称金额预算可精确阻断；补用量/次数/并发与未知成本处理，复用 MAM 预算语义 |
| 设计助手对新节点支持 | 未找到 component_task/asset-bundle 的专门设计提示或模板 | 补生成、校验、编辑和预览的验收用例，不把 schema 可解析视作完整设计支持 |
| 原图/视觉引用重开 | Spine/星图桥使用临时 references Map | 桥兼容性风险已确认，真实项目是否保留该附件需复测；不能直接断言所有重开均失败 |
| 验收记录可追溯性 | traceability 只有六个 latest.json，未绑定当前源码/包哈希 | 每条需求绑定基线、包/资源版本、平台、样本、操作和结果；旧证据不能自动代表新版本 |

## 持续继承 LevelUp 更新：现状与目标

已具备只读快照、固定提交/文件哈希、source map、三方合并、补丁重放、新依赖审查和一次真实 YuE2 规范化修复继承。不能把这些扩展解释为 Rust→TypeScript 适配语义可以自动同步。

后续标准流程应为：获取已提交上游 → 按组件列差异 → 自动重放 UI/纯函数改动 → 标记原生/协议改动供人工适配 → 对等与合同测试 → 候选包 → 原版本运行中升级/回退演练 → 用户选择安装。每次报告哪些变更自动继承、哪些需人工处理和哪些尚未支持。

成功标准：至少各演练一次 UI 更新、业务函数修复和原生协议变更；在宿主 API 未变时只升级目标组件，旧 Attempt 不变，回退后原工程可读。不是承诺未来所有上游更新都能无人值守合并。

## 后续实施顺序与工期

以下为剩余工作的初步工程人日，1 人日约 6–8 小时有效工作。包含适配和针对性测试，不是多 Agent 的运行时估算。真实服务授权、模型下载、合适 GPU、macOS 设备和 Spine 编辑器等待时间另计。完成第一阶段后依据实际缺口重估。

| 阶段 | 具体交付与验收出口 | 估算 | 依赖/并行方式 |
| --- | --- | --- | --- |
| R0 收紧状态与执行策略 | 50 项记录改为实现/fixture/真实验收分层；统一 component_task/Role 权限批准；建立失败用例 | 1–2 人日 | 立即开始；本报告已完成状态审计部分 |
| R1 补齐独立运行和升级边界 | 稳定宿主 RPC；业务 runtime 随组件版本；Attempt 固定版本/哈希；业务 API 与可关闭 UI 的后台执行；先完成代表组件再迁移其余 | 8–12 人日 | 先固定契约；与 UI 对等清单并行，不能让多个 Agent 同时改公共协议 |
| R2 完成 MAM 交付闭环 | 项目上下文、手动成果选入、Role 成果提交、正式 Artifact/审核/下游；显式跨克隆交付；设计助手和预算边界 | 6–10 人日 | 依赖 R0 和 R1 契约，可先做库/UI适配 |
| R3 补齐原功能差异 | 星图真实会话、文件内容、多图；跨台导航；写作/Spine 业务操作；参数/事件/引用重建；3D安装恢复和轻量rig | 6–10 人日 | 与 R1/R2 并行；按组件分工，统一桥接口由主审集成 |
| R4 真实环境验收与修复 | 在线图片/视频/语音/写作；Spine全流程；音乐逐引擎；3D形状→贴图→绑定→导出；Windows故障恢复、macOS可用能力 | 7–12 人日 | 各组件完成即可滚动验收；8GiB显存不能默认满足所有引擎 |
| R5 更新演练与可维护交付 | 三类真实上游更新、安装升级回退、证据绑定；与原 MAM 变更集成；发布者签名/目录和安装文档 | 4–6 人日 | R1 后可提前做同步演练，正式发布依赖 R2–R4；在线自动分发可单独排期 |

总量约 **32–52 人日**。采用三个并行执行流、一个主审集成时，建议先按 **4–6 个工作周**安排完整收尾；不能把人日简单除以 Agent 数。若真实引擎/设备等待或上游资源不兼容超出预期，需另行调整。仅内部离线使用时，可暂缓 R5 的在线分发部分，不可暂缓权限、成果交付和升级可追溯性。

建议分工：A 负责 runtime/版本/来源同步；B 负责 MAM 权限、Artifact 和交付；C 负责工作台对等和原生资源；主审负责公共契约、集成回归、证据和版本。R4 按已完成组件滚动开展，避免最后才发现真实资源不匹配。

第一个可见里程碑应是“图片生成 → 写作引用 → 作为正式成果提交 → 人工审核 → 下一角色消费”的真实 MAM 流程，同时证明仅升级该组件可以继承一次上游修复。两项一起通过后，再按同一标准签收音乐、Spine、3D和星图；不再用组件数量作为完成标准。

## 当前如何使用与下一步边界

现有 Windows 预览仍可用于检查入口和已接操作：`release/start-creative-preview.cmd`，组件目录 `release/creative-components/0.1.42/`。它使用独立数据目录，尚未合并进原 MAM 工作区；直接打开原 MAM 不会自动看到本分支全部改动。

当前只适合开发验收。下一步优先 R0，再固定 R1/R2 契约并行补齐；不是要求用户先把全部模型装好来弥补实现缺口。开展真实验收时才需要可用 Provider/模型、选定引擎及设备；凭据通过 MAM 设置管理。

本次仅审计和修正文档，没有修复以上代码、变更数据 schema、合并主分支或发布。LevelUp 继续只读。既有本地测试事实保留，但任何“全部完成、只剩实机测试”的解释以本报告纠正后的状态为准。
